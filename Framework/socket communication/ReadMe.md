# Universal Socket File Transfer Module

## Overview

This module provides a robust, cross-platform solution for **automated, bi-directional file transfer** between any SDN project nodes—Raspberry Pi clusters, Windows controllers, and Linux validation servers. It enables the seamless exchange of `.py`, `.conf`, `.json`, and any other files required for LLM-driven SDN configuration and iterative testing, using a simple socket-based protocol.

**Key Features:**
- Bi-directional file transfer (`GET` and `PUT`) via TCP sockets.
- Supports any file type—main SDN configs, device node `.conf` files, topology `.json`, logs, etc.
- Multi-platform: Works on Linux, Raspberry Pi, and Windows (with Python 3).
- Easy integration into automated SDN workflows and pipelines.
- Ready for expansion (see "Extensibility" below).

---

## Components

- **file_server.py**  
  A universal file server to be deployed on every node (edge device, controller, validator). It listens for both download (`GET`) and upload (`PUT`) requests and serves as a unified hub for all file exchanges.

- **file_client.py**  
  The command-line tool to upload or download any file between machines using the server.

## Usage

### 1. Deploy the File Server

On each machine that needs to send or receive files (Raspberry Pi, Windows, Linux):

```bash
python3 file_server.py
```
Change BASE_DIR in the script to your desired storage directory.

2. Download a File from a Remote Server
On the machine that needs the file, run:

python3 file_client.py GET filename.ext remote_host port local_save_dir


Example:
Download node3.conf from a Raspberry Pi at 192.168.1.111:
python3 file_client.py GET node3.conf 192.168.1.111 61000 ./downloads/

3. Upload a File to a Remote Server
On the machine with the file to upload, run:
python3 file_client.py PUT filename.ext remote_host port local_file_path
Example:
Upload experiment_topo.py to a Linux validation server at 192.168.1.222:
python3 file_client.py PUT experiment_topo.py 192.168.1.222 61000 ./generated/experiment_topo.py

4. Supported Scenarios
Transfer of .py main SDN config files (generated by your LLM edge models).

Transfer of .conf files for device-specific details or iterative node configuration.

Transfer of .json topology files, logs, or any other artifact required in your SDN workflow.

Seamless data exchange between heterogeneous systems in a LAN.

Extensibility & Advanced Use
Any file type:

Multi-threaded:
The server can handle multiple concurrent clients.

Integration:
Easily plug this system into automated CI/CD pipelines, SDN experiment scripts, or custom tools. Wrap client calls in Python, Bash, or batch scripts as needed.

Cross-platform:
Works on Linux, Windows, and Raspberry Pi with Python 3.

Future-proof:
To support authentication, encryption, or additional metadata, the protocol and scripts can be extended with minimal effort. (Get in touch or fork for your requirements!)

Troubleshooting & Recommendations
Ensure all participating machines are on the same LAN and firewall rules allow the configured PORT.

Always run file_server.py with sufficient permissions to read/write to BASE_DIR.

Adapt BASE_DIR and port assignments to your deployment environment for security and convenience.

For bulk or batch transfers, loop your file_client.py calls in your workflow script.

Example SDN File Exchange Flow
Step 1: LLM model on Raspberry Pi generates experiment_topo.py and r2.conf, stores them in its output directory.

Step 2: Controller uses file_client.py GET experiment_topo.py ... to pull the file for review or editing.

Step 3: After edits or new config generation, controller uses file_client.py PUT r2.conf ... to send new files to a validation server.

Step 4: The validation server receives files in its exchange directory, ready for automated pytest or custom verification.

Honest Notes
This solution is minimal by design. It does not provide built-in encryption or authentication—add these as needed for production or WAN environments.

For SDN research, rapid prototyping, and controlled testbed environments, this module is simple, reliable, and easy to debug.
